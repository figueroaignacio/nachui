1. DEPENDENCIA CIRCULAR ENTRE LA WEB Y LA API
===============================================================================

DocsService hace fetch a ${FRONTEND_URL}/api/docs (docs.service.ts:26), y el
chat de la web pega contra esta API. El grafo queda web -> api -> web. Si el
frontend está caído, la API no puede servir docs.
packages/ai/src/scripts/ingest.ts:29 tiene el mismo problema: sale a buscar
frontendUrl/api/docs para armar los embeddings.

Los MDX están en apps/web/src/content/, a dos carpetas de distancia dentro del
mismo monorepo. Proponé y aplicá una de estas dos, justificando la elección:

  - Mover el contenido a un packages/content que consuman la web, la API y el
    script de ingest directamente.
  - Que la web publique los docs a la API en el build, invirtiendo la
    dirección de la dependencia.

Hay un agravante que resolver en el camino, cualquiera sea la opción que
elijas. apps/web/src/app/api/docs/route.ts devuelve
`ContentRepository.getDocs()` sin filtrar por `published`, mientras el resto de
los consumidores de docs en la web sí filtran. O sea que este endpoint sirve
borradores, y los dos clientes de arriba se los llevan:

  - la API los expone en /docs
  - el ingest los mete en los embeddings, así que salen citados en las
    respuestas del asistente

Hoy hay al menos un documento afectado: apps/web/src/content/docs/en/
installation.mdx no tiene `published` en el frontmatter y el default del schema
es false. El prompt A lo arregla en su fase 0, pero el filtro faltante es un
problema de este contrato, no de ese archivo. Cerralo acá.

2. EL DTO DEL CHAT VALIDA MENOS DE LO QUE PARECE
===============================================================================

create-chat.dto.ts completo:

    @IsArray()
    @IsNotEmpty()
    messages!: UIMessage[];

Verifica que sea un array no vacío y nada más. Sin @ValidateNested() +
@Type(), los items no se validan, whitelist: true no los limpia y llegan
objetos arbitrarios a pipeAgentUIStreamToResponse. Tampoco hay tope de largo
del array ni de tamaño por mensaje.

Agregá validación de los items, un máximo de mensajes en el historial y un
máximo de caracteres por mensaje. Ojo que UIMessage viene del AI SDK y es un
type, no una clase: vas a necesitar una clase DTO propia que lo represente para
que class-validator pueda recorrerla.

4. LA TAXONOMÍA DE `type` NO REFLEJA LA REALIDAD
===============================================================================

En packages/db/src/schema.ts:10:

    type: text('type').$type<'ui' | 'hook' | 'utils'>().default('ui')

Ese enum no contempla 'layout' ni 'ai'. Los valores 'hook' y 'utils' no los
popula nada. Y ya está forzando un parche en scripts/sync-registry.ts:101:

    await processDirectory(LAYOUT_COMPONENTS_ROOT, 'ui');
    // Keeping type 'ui' as per DB schema if it doesn't have 'layout'

El script sabe que layout es una familia distinta (la firma de processDirectory
es `type: 'ui' | 'layout'`), la calcula, y la fuerza a 'ui' porque el enum no la
contempla.

Contexto: la documentación ya se reorganizó en elements/ui y elements/layout,
con elements/ai planificado. Además, `slug` es .unique() global (schema.ts:6), y
toda la interfaz del CLI es `nachui add <slug>` sobre ese namespace plano. Los
nombres probables de elementos de IA (message, prompt-input, chat, avatar,
card, input) incluyen varios que YA EXISTEN como componentes de UI. Cuando se
agregue el primero, el constraint de unicidad hace fallar el sync o
sobreescribe el componente existente.

NO implementes todavía. Presentá al usuario las opciones y trade-offs para:

  a. Si `type` pasa a ser la lista real de familias, y qué migración implica.
  b. Si `slug` sigue siendo global o pasa a ser compuesto (ui/button,
     ai/message), y qué implica para nachui add / list / remove.

Esperá la decisión antes de tocar el schema. Es una migración chica hoy y una
con datos en producción después.

Este punto es el mismo que el paso 2.1 del prompt A. Si los dos prompts se
corren, la decisión se toma una sola vez y los dos la respetan.
