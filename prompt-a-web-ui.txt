--- 2.1 El problema de taxonomía (PROPONER, NO IMPLEMENTAR) ---

Hoy conviven tres vocabularios para el mismo concepto:

  Contenido docs : elements/ui, elements/layout, y en el futuro elements/ai
  Código         : packages/ui/src/components/, src/layout/, src/bricks/
  Base de datos  : type: 'ui' | 'hook' | 'utils'

La columna `type` en packages/db/src/schema.ts:10 no contempla 'layout' ni
'ai', y 'hook'/'utils' no los popula nada. Eso ya está forzando un parche en
scripts/sync-registry.ts:101:

    await processDirectory(LAYOUT_COMPONENTS_ROOT, 'ui');
    // Keeping type 'ui' as per DB schema if it doesn't have 'layout'

El script sabe que layout es una familia distinta, la calcula (la firma de
processDirectory es `type: 'ui' | 'layout'`), y la fuerza a 'ui' porque el enum
no la contempla.

Hay una tercera familia planificada, elements/ai. Antes de que exista hay un
riesgo concreto: `slug` es .unique() global en el schema (schema.ts:6), y toda
la interfaz del CLI es `nachui add <slug>` sobre ese namespace plano. Los
nombres probables de elementos de IA (message, prompt-input, chat, avatar,
card, input) incluyen varios que YA EXISTEN como componentes de UI. El día que
se agregue el primero, el constraint de unicidad hace fallar el sync o
sobreescribe el componente existente, y `nachui add input` queda ambiguo.

Presentá al usuario las opciones y sus trade-offs para estas tres decisiones,
y esperá su respuesta:

  1. ¿`slug` sigue siendo global, o pasa a ser compuesto (ui/button,
     ai/message)? Si es compuesto, el CLI tiene que aceptar las dos formas y
     desambiguar solo ante colisión. Detallá qué implica para
     `nachui add`, `nachui list` y `nachui remove`.

  2. ¿`type` en la DB pasa a ser la lista real de familias? Es una migración
     chica ahora y una con datos en producción después.

  3. ¿Los directorios de código se renombran para coincidir con la taxonomía
     de los docs? ¿elements/ai vive dentro de packages/ui o el paquete se
     separa?

--- 2.2 El generador (implementar después de 2.1) ---

Quedan tres catálogos del mismo dominio mantenidos a mano:

  COMPONENT_REGISTRY  packages/ui/src/lib/registry.ts
                      componente -> path
  DEMO_REGISTRY       mismo archivo, 290 líneas entre los dos
                      componente -> variante -> path
  DEMO_COMPONENTS     apps/web/src/shared/components/mdx/demo-registry.tsx
                      componente -> variante -> componente React  (288 líneas)

DEMO_REGISTRY y DEMO_COMPONENTS tienen las mismas claves en la misma
estructura anidada; uno guarda el path, el otro el import. Agregar una
variante hoy son tres ediciones y ninguna falla en compilación si te olvidás
una. navigation-menu, el componente más nuevo, entró así.

Escribí un script de codegen en packages/ui que escanee el filesystem y emita
los tres. Enganchalo al build de Turbo y hacé que falle si el archivo generado
quedó desactualizado respecto del disco, para que CI lo detecte.

CRÍTICO: el generador debe estar dirigido por una lista de familias declarada
en UN SOLO LUGAR, no por directorios hardcodeados. Algo del estilo:

    const FAMILIES = [
      { id: 'ui',     codeDir: 'src/components', docsSegment: 'elements/ui' },
      { id: 'layout', codeDir: 'src/layout',     docsSegment: 'elements/layout' },
    ];

Agregar 'ai' tiene que ser una línea en ese array, no una edición del scanner.
La forma exacta depende de lo que se resuelva en 2.1.

Antes de empezar, leé scripts/sync-registry.ts en la raíz del monorepo. Ya
hace este escaneo para poblar la tabla components de Postgres, incluida la
extracción de dependencias desde los imports. Reusá esa lógica en vez de
reescribirla; idealmente extraé el escaneo a un módulo compartido que usen los
dos.

Tres cosas que NO podés romper:

  - `as const` es obligatorio. get-component-code.ts hace
    COMPONENT_REGISTRY[name as keyof typeof COMPONENT_REGISTRY]. Si el
    generador emite Record<string, string>, ese keyof colapsa a string, el
    narrowing desaparece sin un solo error de compilación y el único guard que
    queda es el chequeo en runtime. Emití un objeto literal cerrado con
    `as const`.

  - Los componentes viven en más de un directorio. flex, stack, grid y
    container salen de packages/ui/src/layout/, el resto de src/components/.

  - El CLI no usa este registry. Resuelve componentes contra
    ${API_URL}/registry, que sirve desde Postgres. Confirmá que sigue así.

FASE 3: SACAR EL PUENTE _sync DEL CHAT
===============================================================================

apps/web/src/features/chat/store/chat-engine.tsx:48 espeja TODO el estado del
hook useChat dentro de un store de Zustand, vía un useEffect con once
dependencias que escribe diez campos.

Tres problemas concretos:

  - Doble fuente de verdad, siempre un render atrasada. Durante el streaming
    cada token dispara el efecto y re-renderiza a todos los suscriptores.

  - Falla silenciosa: los valores iniciales del store son stubs
    (chat-store.ts:49, `sendMessage: async () => {}`). Si ChatEngine no está
    montado, o monta después de un consumidor, triggerExplanation desde
    doc-actions.tsx llama al no-op. Sin error, sin warning: el botón no hace
    nada.

  - messagesEndRef, que es un RefObject de React, vive en un store global
    (chat-store.ts:20).

Rediseñalo: Zustand se queda solo con isOpen, isExpanded y una cola de prompts
pendientes. El estado del chat se queda en el hook y se expone por Context.
triggerExplanation empuja a la cola y el componente del chat la drena cuando
monta. Eso elimina el _sync, los stubs y la carrera de montaje.

No toques hooks/use-chat.ts más de lo necesario: está bien hecho, usa las
partes tipadas del AI SDK y es la referencia.

Aviso: la UI del chat cambió bastante desde la última vez que se miró esto
(chat-loading.tsx se borró, chat-reasoning.tsx es nuevo, chat-header y
chat-message se reescribieron). El store y el engine no se tocaron, así que el
diagnóstico sigue igual, pero revisá quién consume el store hoy antes de
cambiarle la forma.
